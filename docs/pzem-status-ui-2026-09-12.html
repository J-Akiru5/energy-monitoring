3. PZEM_OFFLINE Operator Notification

The exact wording designed into the backend is present and rendered:

  • Created with message "Phase <X> communication failure — inspection required. Check wiring, connector, sensor power, or the communication path." — apps/web/src/app/api/ingest/route.ts:41 (via firePzemOfflineAlerts()).
  • Rendered on the admin Alerts page: apps/admin/src/app/alerts/page.tsx:146 prints {alert.message}, with a dedicated PZEM_OFFLINE icon at line 40.
  • The PZEM Status page additionally shows per-phase HEALTHY/OFFLINE and "Offline since …" from device_alert_state (apps/admin/src/app/api/devices/pzem-health/route.ts).
POTENTIAL BUG — alert may not reach customer-scoped operators

createAlert() inserts without customer_id (packages/database/src/queries/alerts.ts:28-38), but getUnreadAlerts(customerId) filters .eq("customer_id", customerId) (:81). alerts.customer_id was added by migration 20260910120001_phase3a_additive_columns.sql; there is no trigger/default to populate it. Newly ingested PZEM_OFFLINE alerts therefore have NULL customer_id and are filtered out of /api/alerts for normal customer users. They are visible only to Super Admins, whose query is unscoped (apps/admin/src/app/api/alerts/route.ts:29-31). The doc comment on createAlert() claims callers set customer_id "through the TenantStamp" — but the stamp is applied only to power_readings, never to alerts. This is pre-existing (not introduced by this branch) but it directly limits the operator notification required here.

4. Other Findings

4.1 Frontend/backend discrepancy — phaseMode is never supplied

apps/admin/src/app/pzem/page.tsx:89 reads overviewData.phaseMode from /api/overview?deviceId=…, but apps/admin/src/app/api/overview/route.ts takes no request parameter and returns no phaseMode. Result: the entire 1-phase source-selection panel is dead code from the UI's perspective. Minimal fix would be to expose the EMU phase_mode (already available via emu_configurations.phase_mode in packages/database/src/queries/tenant.ts) on a device-scoped route. Not implemented in this branch — reported only.

4.2 Admin pzem-health / pzem-config routes have no session guard

Unlike the other admin API routes (alerts, overview, devices), the two new PZEM routes do not call resolveAccess(). pzem-config lets any caller read/write source mode for any deviceId; pzem-health reads any device's alert state. Reported only; no change made.

4.3 Real firmware on develop does not emit the failover fields

firmware/src/monitor.cpp on this branch has no pzemActiveSource/ pzemSourceMode, so until the firmware branch lands, real 1-phase payloads will not carry an active source and behaviors 2a/4/5 have no live producer. This is an integration dependency, not a defect in this branch.
