Fix — Redundant-Tap Guard

localTrip + blackout voltage: Uses active source in 1-phase mode.

6. Addendum — Unreachable Branch in the sensorOffline Shortcut

Bug: every total-loss event reported as "Phase A offline" only

The sensorOffline shortcut synthesized its phase flags like this: 

const is3PhaseOff = isThreePhasePayload(payload);
const phaseFlags = is3PhaseOff
  ? { A: true, B: true, C: true }
  : { A: true, B: false, C: false };  // ← always taken

The shortcut payload never includes a threePhase key — confirmed against firmware/src/monitor.cpp, which sends only { deviceId, timestamp, sensorOffline: true, phaseMode } whether triggered by 3-phase total loss or 1-phase AUTO exhausting A/B/C. isThreePhasePayload() is therefore always false here: the all-true branch was dead code, and every real total-loss event was recorded as a Phase A communication failure.

Fix: the flags are now unconditional — { A: true, B: true, C: true } — since the condition that triggers the shortcut (all raw phases offline) is unified across both modes. The phaseMode field is irrelevant to this path; no narrower case exists.

Callers audited: the shortcut is consumed only by POST /api/ingest. firePzemOfflineAlerts()'s other caller (the normal 3-phase path) passes real per-phase flags from sensor readings and is unaffected. No consumer reads phase information back from the shortcut response ({ status: "ok", sensorOffline: true }).
