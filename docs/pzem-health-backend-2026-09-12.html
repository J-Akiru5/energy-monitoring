2. Safety Bug Fix — Offline Phase Threshold Guard

Bug: offline phases could auto-trip the relay

A dead PZEM reports voltage: 0 (NaN zeroed by readPhase()), which is < thresholds.undervoltage (default 200V) by definition. Without the guard, checkThreePhaseThresholds() would fire an UNDERVOLTAGE fault and potentially auto-trip the relay on a communication failure, not a real electrical condition.

Fix: Skip OV/UV/OC evaluation for any phase where phase.data.offline === true. Also clears any pending spike timers for that phase (the fault condition is a comm failure, not electrical).

3. Alert Engine Integration

The firePzemOfflineAlerts() helper reuses the existing processFaultCondition() engine verbatim — same 60s spike window, same 30s recovery debounce, same device_alert_state dedup key. No new alert-engine code paths were created. 

firePzemOfflineAlerts(deviceId, phaseFlags, activeStates)
  for each phase [A, B, C]:
    processFaultCondition({
      deviceId, type: "PZEM_OFFLINE", phase,
      isFault: phaseFlags[phase], ...
    })

Unified, not a special case: The legacy sensorOffline shortcut (which fired one non-phase-specific phase: '' alert) now calls the same helper, synthesizing all phases as true. The phase: '' variant of PZEM_OFFLINE stops being written going forward; historical rows are left alone.

  409: { "status": "error", "error": "PZEM-X is currently unavailable..." }

4.2 Config Table Proposal (awaiting Jeff's confirmation)

Proposed: new pzem_config table

A dedicated pzem_config table, 1:1 with devices (device_id PK), following the identical shape as relay_config. Columns: device_id (uuid PK), mode (text, 'auto'|'manual'), manual_source (text, 'A'|'B'|'C'|null), updated_at (timestamptz).

Why a sibling table, not extending relay_config: relay_config already has 11 columns of its own; adding pzem-specific columns would couple two independent concerns. A dedicated table keeps each config surface clean and independently evolvable.

Status: AWAITING CONFIRMATION — route works regardless of storage (defaults to AUTO when no row exists). Migration will be written only after Jeff confirms.

4.3 Offline-Phase Rejection

PUT handler checks getAlertState(deviceId, "PZEM_OFFLINE", manualSource) before persisting. If the phase is currently in an active OFFLINE incident, returns HTTP 409 with the exact error message from the architecture doc. Rejection happens before persisting, not accept-then-ignore.

5. Mock Sensor Extension

The mock sensor now supports per-phase offline simulation via environment variables: 

MOCK_PHASE_A_OFFLINE=true   # Simulate Phase A communication failure
MOCK_PHASE_B_OFFLINE=true   # Simulate Phase B communication failure
MOCK_PHASE_C_OFFLINE=true   # Simulate Phase C communication failure

When flagged, the phase returns zeroed readings with offline: true, matching the firmware's behavior when a PZEM is unreachable. This allows the entire alert engine (firing, 60s promotion, 30s recovery, safety guard) to be exercised with zero physical hardware — the CODE-VERIFIED layer per architecture doc Section 10.
