What was delivered

A complete light mode for the system, switchable at runtime with one click:

  • A shared theme token layer — packages/ui/src/theme.css is now the single source of truth for every design token in the platform, used by all three apps. Framework-agnostic, no new dependencies.
  • The light palette — canvas #F8FAFC, white surfaces, slate-800 text, cyan-600 primary accent. Matches the “Industrial Cool Light” palette that was already documented in the repo’s design constitution but never implemented.
  • Every hardcoded color migrated — backgrounds, borders, glass panels, inputs, badges, status colors, dialogs, charts, and tooltips across all three apps now resolve through tokens that flip with the theme (with dark values preserved exactly).
  • A theme toggle in each app’s chrome — top bar (web), sidebar + mobile top bar (admin), header (super-admin), and the login screens of all three.
  • No-flash persistence — the theme is applied by an inline script before first paint, so a user who picked light mode never sees a dark flash on load.

How the theme system works

Light mode is opt-in via a data-theme="light" attribute on the <html> element. Everything else is CSS custom properties, which means no component logic branches on the theme and no re-render is needed when switching — the browser restyles instantly.

1 · Token layertheme.css defines all tokens twice: dark values on :root, light overrides under :root[data-theme="light"].
2 · Pre-paint scriptA tiny inline script in each app’s layout reads localStorage and sets the attribute before first paint — no flash.
3 · ToggleThe shared ThemeToggle component flips the attribute, persists the choice, and keeps the mobile browser-chrome color in sync.
4 · Component CSSAll app styles reference tokens (var(--canvas), rgb(var(--line-rgb) / 0.6)) instead of literals, so both themes stay consistent automatically.

A key migration technique: recurring translucent colors (glass panels, borders, scrims) became RGB triplet tokens. For example, the old literal rgba(15, 23, 42, 0.88) is now rgb(var(--canvas-rgb) / 0.88). In dark mode the triplet --canvas-rgb is 15 23 42 — the exact same pixels; in light mode it is 255 255 255 — the glass panel becomes white. One token, both themes, no per-rule overrides.

Zero dark-mode drift

Every token’s dark value was seeded with the literal it replaced, and verification compared computed styles before/after: the dark theme renders identically to the pre-change build, checked down to the RGBA values on panels, inputs, buttons, and banners.

Charts & tooltips

Charts are the easiest place for a theme switch to look broken, so they got dedicated treatment:

  • Grid lines, axis lines, and tick labels are re-pointed at --chart-grid / --chart-axis via CSS rules that override the SVG attributes Recharts renders — so no chart prop had to change and every chart follows the theme at once.
  • Tooltips (dashboard, phases, history, sensors, admin reports) now reference --tooltip-bg / --tooltip-border. In light mode they render as white cards with soft borders instead of dark slabs.
  • Phase colors (A/B/C) moved to --phase-a/b/c tokens: rose/amber/cyan in dark, deeper rose/amber/cyan-600 in light. The token values resolve inside SVG presentation attributes (verified in-browser), so the same color strings work for chart strokes, gradients, and HTML labels.

The single-metric report charts (admin) use the same accent tokens, and the PDF export now captures against the active theme’s canvas color instead of a hardcoded dark background — a light-mode PDF is light, a dark-mode PDF is still dark.

Toggle & persistence

Mechanics worth knowing for support and future work:

  • Storage key: em-theme in localStorage per origin ("light" or "dark"). Absent key = dark, so existing users see no change until they opt in.
  • No flash: each root layout renders a small inline script before the app shell; it sets data-theme on <html> from storage before the first paint. This is why the script is inline and undeduplicated in layout.tsx files — that is intentional, not cleanup debt.
  • Accessible: the toggle is a real <button> with a dynamic aria-label (“Switch to light mode” / “Switch to dark mode”) and a visible focus ring.
  • Mobile chrome: the web app also updates its theme-color meta to #F8FAFC in light mode so the browser/status bar matches the app.
  • Hydration-safe: <html> carries suppressHydrationWarning because the pre-paint script legitimately mutates it before React hydrates.

Deploy & rollback

  • Deploys with the next Vercel build of web, admin, and super-admin — no database, env, or infrastructure changes. Pure front-end.
  • Dark mode remains the default. Nobody’s experience changes unless they use the toggle, so this can ship safely ahead of any demo.
  • Rollback is a normal revert of the feature branch — the only persisted state is a localStorage key that is ignored by older builds.
  • Follow-ups if desired: respect prefers-color-scheme on first visit (so OS-level light preference defaults to light), and adding the toggle to any future screens.
