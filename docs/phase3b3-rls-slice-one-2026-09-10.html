Summary

Every query in this codebase runs through getSupabaseAdmin() (service role), which bypasses RLS entirely. This slice proves the full two-layer pattern on one path — power_readings reads via /api/readings — before it gets replicated across the other 8 query files:

  1. Application-layer scoping (the actual isolation boundary today): resolveAccess() resolves which customer a logged-in user is authorized for, and that customerId is passed down into query functions, which add an explicit .eq('customer_id', ...) filter.
  2. RLS policies (defense in depth / backstop for future user-context queries): enabled on the 7 core tables in the customer → site → building → EMU → controller → power_readings chain.

Unplanned fix: tenant-stamping was silently broken

While generating test readings via mock-sensor, power_readings.customer_id came back NULL on every insert. Root cause: lookupControllerByDevice() in packages/database/src/queries/tenant.ts tried to embed emu_installations directly under controllers in a Supabase nested-select — but there's no foreign key between those two tables (only controllers → emus → emu_installations). PostgREST returned PGRST200: Could not find a relationship, and that error was silently swallowed by the function's graceful-degradation path (if (error || !data) return null), so /api/ingest kept accepting readings and just never stamped them — no error surfaced anywhere.

Blast radius: WVSU's real device has 92,559 correctly-stamped rows from the original Phase 3a backfill and 0 NULL-stamped rows — its last reading is from 2026-04-28, so it hasn't sent live telemetry since before this bug could bite it. But the moment any real device resumes sending, every new row would land with customer_id = NULL — invisible under both RLS and the explicit filtering this task just added. That would look like "the dashboard went empty," not a security bug.

I stopped and asked before touching this since it's outside readings.ts. You said fix it now — done: the query now embeds emu_installations under emus (where the FK actually is), and correctly filters both emu_installations and emu_configurations for the currently-active row (ended_at IS NULL) instead of taking an arbitrary first result. Verified with a fresh mock-sensor run after the fix — see below.

Known gap, flagged not fixed

getLatestReading and getMonthlyEnergy have customerId as optional rather than required, because each has a caller with no session to resolve access from:

  • /api/heartbeat — a Vercel cron job that iterates all devices with no user context.
  • /api/billing — currently unauthenticated (deviceId-only, no login check at all).

Both still query unscoped, exactly as before this task. This is a real gap, not a security fix — it's called out explicitly (in code comments and here) rather than silently left as-is, and belongs to the follow-up task that covers the other 8 query files.
