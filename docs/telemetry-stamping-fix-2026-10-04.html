Telemetry Tenant Stamping Fix

Follow-up to the RM-03 finding. Four telemetry write paths — createAlert, logRelayAction, startBlackoutEvent, startAlertIncident — never set customer_id/emu_id, leaving 428 live rows unstamped: invisible to every non-service-role caller under RLS, and invisible to customer-scoped read paths like getUnreadAlerts() and getRelayLogs(). The writers now resolve the tenant stamp at write time, and an idempotent backfill migration repairs the historical rows. Both are committed locally; neither is deployed or applied under the current hold.

The gap

Phase 3a added customer_id/emu_id to alerts, relay_logs, blackout_events, and device_alert_state, and the backfill migration stamped the rows that existed then. But the write paths never populated the columns — only insertReading did (via the ingest route's stamp). The createAlert JSDoc even claimed callers "set customer_id through the TenantStamp already stamped on the insert" — the insert had no such field.

No cross-tenant leak: RLS is fail-closed for NULL stamps. The impact is the opposite — the owning customer couldn't see their own recent rows.

The fix

  • Write paths resolve the tenant stamp via lookupControllerByDevice() — the same device → controller → EMU bridge ingest and the RLS policies use — and write customer_id + emu_id. If the device has no controller bridge the stamp stays NULL: fail-closed, matching ingest's graceful degradation.
  • Backfill migration 20261004000002_backfill_telemetry_stamps.sql — five idempotent UPDATEs (only rows with customer_id IS NULL), joining each row's device to its ACTIVE controller's EMU. power_readings gets customer_id + emu_id only: the recording-time installation isn't knowable for historical rows, and stamping the current one would be false.
