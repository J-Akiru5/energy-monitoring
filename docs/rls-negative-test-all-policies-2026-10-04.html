Why this test exists

RM-03 asked for a negative test per RLS policy and a pass/fail result per table — not a summary claim. Recon for this item found the prior evidence didn't meet that bar:

  • The existing negative-test-devices-rls.ts never exercised RLS. It runs entirely through getSupabaseAdmin() (service role, which bypasses RLS by design) and then simulates the policy logic by querying with explicit customer IDs. Its own step 5 says so: "Since we can't easily get a JWT here, we'll verify the SQL logic…". It proves the query logic works — it does not prove the database isolates tenants.
  • The slice-one "negative test" was API-layer, not RLS-layer. The 2026-09-10 report tested /api/readings through a running web server, which exercises resolveAccess() + explicit application scoping. That's the app's primary isolation boundary — but again not the RLS policies themselves.
  • So real per-policy RLS evidence was ~0 of 12, not 2 of 12 as the roadmap's first pass estimated. This suite closes that gap at the database layer.

All 12 policies are SELECT-only ("members read own customer") and were applied by migrations 20260910220000_phase3b3_rls_core_tables.sql (7 tables) and 20260910230000_phase3b3_rls_telemetry_tables.sql (5 tables). Write policies are explicitly out of scope in those migrations and remain a follow-up.

Method

Two disposable test users — one per tenant — sign in through the real auth endpoint and query PostgREST with their own JWTs. The database applies the RLS policy exactly as it would for a browser session. A service-role sanity check confirms the other tenant's row genuinely exists, so a "0 rows" result can never pass vacuously.

For each of the 12 tables the suite records four booleans — A→A, A→B, B→B, B→A — plus a service-role existence check for both fixture rows. The table passes only if all six conditions hold. The suite defaults to a read-only dry run; --execute is required before it creates missing fixtures or rotates the disposable test users' passwords.

Scope note

What this proves — and what it doesn't

This proves the SELECT policies isolate reads for authenticated members. It does not test write policies (none exist yet — out of scope by the migrations' own design), nor service-role paths (which bypass RLS by definition and rely on application-layer scoping). The policies tested are the DB-level backstop.

Findings beyond the test

New finding

Four telemetry write paths never tenant-stamp their rows

RLS is fail-closed for rows with customer_id = NULL — they're invisible to every non-service-role caller. That's safe, but a read-only scan of live data shows the app's own writers leave rows unstamped, which also hides them from the app's customer-scoped queries (e.g., getUnreadAlerts() and getRelayLogs() both filter by customer_id):

  • relay_logs — 168 of 181 rows have NULL customer_id (logRelayAction() never sets it)
  • alerts — 246 of 13,032 NULL (createAlert() never sets it)
  • blackout_events — 9 of 23 NULL (startBlackoutEvent())
  • device_alert_state — 5 of 12 NULL (startAlertIncident())
  • power_readings — 4 of 96,286 NULL (ingest stamps via the controller lookup; residual edge cases)

Net effect: no cross-tenant leak (RLS hides them), but customer-facing alert/relay-log views can be missing recent rows. Fix belongs in a separate item — either stamp at write time (the ingest route's lookupControllerByDevice() pattern) or via DB triggers. Flagged, not fixed here.

Evidence correction

The old "negative test" was a simulation

scripts/negative-test-devices-rls.ts runs through the service-role client for every query and reconstructs the policy predicate in application code. It never sends a user JWT to PostgREST, so it cannot detect a missing or broken policy. It should not be cited as RLS evidence; this suite supersedes it at the policy level (the old script still has value as an application-scoping check, if re-labeled).
