Why the bypass happened

The immediate driver is documented; the systemic reason has to be reconstructed because nothing in the record states a decision to skip staging — the pipeline was simply never operated. Here is what the evidence supports, and what it doesn't.

Driver — documented

Production urgency: a live, expired Super Admin grant

PR #19's own body states the priority: main still only checked revoked_at, so the PR #17 expires_at enforcement had not reached production and "an expired temporary Super Admin grant was still live." The direct develop→main sync was the hotfix. Its PR lifecycle was 18 seconds, with no human review recorded (the only review entry is the Copilot reviewer reporting a quota limit).

Driver — release cadence

13 events in ~60 hours, each individually verified

The sprint ran 2026-09-12 06:05 to 2026-09-14 17:40 UTC. The six develop→main "release sync" PRs each documented their own verification in place of staged validation — merge-tree dry runs, tsc/build/test results, and explicit "firmware byte-identical" checks. Under that rhythm, a develop→staging→main cycle would have serialized every fix behind a staging round-trip.

Driver — firmware isolation

Firmware work was deliberately main-only

Firmware isn't deployed by Vercel, and the field-verified firmware existed only on main while develop's firmware lineage had diverged. The sync PRs protected it explicitly — PR #10 "preserving the already-verified firmware currently on main", PR #15 "firmware byte-identical to main", PR #19 "Firmware on main is untouched by develop". Routing firmware through staging would have added merge risk with no deployment benefit.

Was staging broken or blocking? No — the evidence says it was healthy and simply unused.

  • Its deployment was up. GitHub commit statuses on staging's tip b4ff2c8: Vercel – energy-monitoring-web: success, Vercel – energy-monitoring-admin: success. The Vercel branch gate explicitly allowlists staging builds (scripts/vercel-ignore.sh: main staging develop). There is no record of a staging outage, failure, or block.
  • It was never used in the first place. Zero PRs have ever had staging as base or head (gh pr list --base staging and --head staging both return [] across all 29 PRs). No merge commit in the repo mentions it. Its last commit is also the commit that introduced the staging-validation procedure itself — the pipeline was documented on 2026-09-11, one day before the sprint bypassed it everywhere.
  • As configured, it wasn't a real gate anyway. The procedure doc's own "Known Configuration Traps" (Trap 4) records that staging had no environment separation — all apps shared the same Supabase project and env values as production. A staging validation pass would have run against production data.
  • The rule had no enforcement. main has no branch protection (API returns 404) and no rulesets, and the repo has no CI (no .github/workflows) — so nothing prevented the two direct writes (840161b, bc6a34e) or could have required staging provenance.

What couldn't be determined

No issue, PR comment, commit message, or doc records an explicit rationale for skipping staging. The GitHub issue tracker is empty. So the honest summary is: the immediate drivers (urgency, cadence, firmware isolation) are on the record per-event; the decision to abandon staged promotion is not — staging was documented and then never routed through. Nothing supports the hypothesis that staging was broken or blocking, and that matters: the cause to fix is the process, not an environment everyone was routing around.

Why fast-forward rather than a PR from main into staging

  • Exactness. A GitHub PR merge would create a merge commit on staging, so staging's SHA would differ from main's and every future staging→main promotion would carry crisscross merge topology. A fast-forward makes the refs identical — the cleanest possible starting point for the documented flow.
  • No review value is lost. All 78 commits already passed through their own PRs with verification documented per PR (merge-tree dry runs, builds, tests, firmware checks). A resync PR would re-present the same already-verified content.
  • No rewrite, no force. The push updates staging from b4ff2c8 to bc6a34e where the old tip is an ancestor of the new one — neither a force-push nor a history rewrite. Nothing is discarded; rollback, if it were ever needed, is simply re-pointing staging back to b4ff2c8 (recorded here and still present on the remote branch object).
  • Alternative if the team prefers PR-gated resync: open a PR from main into staging and merge it normally. Viable, and it leaves a PR record — but be aware the merge commit changes the topology as described above. The fast-forward is the technically superior option; the PR option is the one to pick only if process uniformity outweighs that cost.

What now follows

  • staging is now an exact replica of production state — the 23 days of drift ended in one ref move, verified at bc6a34e.
  • Vercel builds and deploys the staging branch from the updated ref (it is in the deploy allowlist), re-materializing the staging environment at main's state.
  • The next production promotion should originate from staging, per docs/staging-validation-procedure.md §13 — which specifies git merge staging into main. It will finally be a real promotion, not a no-op, because staging has been made current first.

Follow-ups worth deciding separately

These are not part of the ref-level fix and don't block it — but RM-00's second half ("stop the direct develop→main path") needs at least a governance decision, or the same bypass recurs on the next hotfix.

Governance

Protect main

There is no branch protection and no ruleset on main today (API 404) — which is how two direct writes got in. A ruleset requiring PRs (plus optional status checks) would stop that class of write. GitHub can't natively require "merged from staging"; that needs a small required status check, which needs CI — and the repo currently has none.

Environment

Make staging a real gate

The staging procedure's own Trap 4 records that staging shared the production Supabase project and env values. Until staging has at least staging-scoped environments (ideally a separate database), "validated on staging" cannot mean what the pipeline claims — and the incentive to bypass it stays high.

Hygiene

develop is also behind main

develop (dc2bd10) is 39 commits behind main and lacks main's 25 main-only non-merge commits — 21 firmware commits, two web fixes, and the credentials script. After the resync, any future develop→staging merge needs the same firmware-preservation check the sync PRs used (empty firmware diff vs main). Worth deciding whether to back-merge main into develop for cleanliness.

Cleanup

Open PR #20 is half-landed

The credentials-reset branch was merged into main directly (840161b) while its PR (#20, against develop) is still open. Merge or close it deliberately so develop and main don't accumulate duplicate-shaped history.

Docs

Correct RM-00's text

The roadmap attributes the gap to 9c3f0e2 alone and implies staging might have been broken. The record shows 13 events and a healthy staging deployment. Worth correcting at the next roadmap revision so the next reader doesn't chase a single-commit story.
