Student Report Defects — Diagnosis & Fixes

WVSU student reports, three defects. All three were reproduced with tests before any code changed, and the two mechanical ones are fixed: PDF generation (a single U+2192 arrow made pdf-lib throw on every request) and row truncation (Reports dropped the newest rows past 5000; History was silently capped at 1000, oldest-first). One shared energy-delta method now serves Reports, PDF, and History. The averages definition is deliberately not changed yet — that changes what a reported number means and needs your approval; the proposal is at the bottom with the exact reproduction of 322.711/day.

Defects & reproduction

Defect 1 — PDF

Every PDF request returned 500: the "Window:" line contained U+2192 (→)

pdf-lib's standard Helvetica uses WinAnsi encoding, which cannot encode →; the throw was caught and returned as a generic 500. Reproduction: the new route test called GET /api/reports/pdf for all 12 metric×phase combinations — 12/12 failed with "expected 200, got 500". Fixed by sanitizing every dynamic string and using -> in the window line; the same 12 cases now return real %PDF bytes. The PDF also now draws the Current point line for every metric (previously power-only), mirroring the reports page's "Current Point" card.

Defect 2 — averages

18.557 kWh over 1.38 h → 322.711 kWh/day

averageDayKwh = totalDelta ÷ span between the first and latest reading in the filtered window; week and month are then day × 7 and day × 30. A short burst makes the span tiny, so the "daily average" explodes. Reproduction: a temporary unit test fed a 1.38 h / ~18.56 kWh burst through buildConsumptionSummary and printed avgDay=322.73, avgWeek=2259.13, avgMonth=9681.98 — the students' 322.711 / 2,258.976 / 9,681.327 exactly. Not changed yet — see the pending decision.

Defect 3 — truncation

Reports dropped the newest rows past 5000; History was capped at 1000, oldest-first

Reports: .order(recorded_at asc).limit(5000) returns the oldest 5000 rows. Reproduction: a 6000-row window with the newest 1000 carrying 10 kWh returned 4.999 kWh instead of ~15 (and the "current point" power came from row 5000, not the newest row).

History: the readings query had no limit/pagination, so Supabase's default max-rows (1000) silently truncated month views. Reproduction against live data (read-only): anchor 2026-09-13, day 1000/1220 rows, week 1000/1426, month 1000/3440 — the month view computed PHP 6.95 instead of PHP 227.18. Current-month data is sparse enough (325 rows) that today's month view happens not to truncate, but any month with >1000 readings does. Unit tests reproduce both the cap (1500-row window → 1000 read) and the method mismatch (a counter reset: last−first = 0 vs the correct 22 kWh).

Fixes

  • Shared energy math — new apps/web/src/lib/energy.ts: monotonicEnergyDelta() (positive deltas, resets ignored) + deltaWithinWindow() + fetchAllPagesDescending(). Reports, PDF (via the summary), and History all use the same delta method now.
  • Paginated reads — both the Reports query and the History readings query fetch all pages via .range(), newest-first, so if the 100k-row page cap is ever hit the oldest data is dropped, never the newest. A page-order bug in the first implementation (rows within each page weren't reversed) was caught by the new tests before commit.
  • PDF — new pdf/_lines.ts builds every line, sanitizing all dynamic strings to WinAnsi (arrow, dashes, curly quotes, bullet, ellipsis, peso sign; anything else becomes ? instead of throwing), and adds the Current point line for kwh/cost/power. The route is now a thin auth + draw loop.
  • Day-bucket deltas — the History week/month chart now carries the previous day's last reading into each day's delta, so per-day values sum back to the window total (they previously lost every cross-midnight increment: 5.962 vs 6 in the test).

Cost-ordering reproduction (step 6)

The complaint "day < week < month should always hold" was reproduced with existing live data — seeding was not needed and live writes were prohibited. Read-only probe, device ESP32-CICT-001, anchor 2026-09-13 (PH):

month10003440PHP 6.95PHP 227.18

Ordering violated in the pre-fix code: day PHP 9.65 > week PHP 6.95. With complete data the ordering holds (13.42 < 13.43 < 227.18). The truncation is therefore the reproduced cause of the ordering complaint — and it is fixed. A second, smaller contributor was the mixed delta method: on 2026-09-14 the capped week showed 0.217 kWh while the true last−first was 0.0000; the shared monotonic method removes that inconsistency. Current-month data (325 rows) never hit the cap, which is why the defect was intermittent.

Pending decision — averages definition

Awaiting approval

Proposed averages (not yet implemented)

  • avg/day = month-to-date kWh ÷ calendar days elapsed this month (PH time, minimum 1 day)
  • avg/week = avg/day × 7
  • avg/month = mean of completed months, falling back to month-to-date when there are none
  • Current month total shown separately (it already is, as "Month")

With this definition the burst example gives ≈ 18.557 ÷ 4 days ≈ 4.64 kWh/day instead of 322.7 — and day ≤ week ≤ month holds by construction.

The dashboard label currently claims "day (last 30d), week (last 8 full calendar weeks), month (last 6 complete months)" — the code does none of that. Once the definition is approved, the label is corrected to match, and the invariant tests are added: day ≤ week ≤ month (kWh and cost), month total = sum of its days, and the 1.38 h burst must not yield ~322 kWh/day. The reports page "Average / Day | Week | Month" cards and the PDF averages section will then display the approved numbers.

Until then the existing averages formula is untouched on this branch — the only pending change is the semantics, not the data plumbing.
