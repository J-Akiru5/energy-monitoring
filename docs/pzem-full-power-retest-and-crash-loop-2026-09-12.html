1. Executive Summary

Crash-Loop Root Cause (CRITICAL)
ESP32-CICT-001 reboots every 40-70 s due to heap exhaustion caused by our loop() re-calling initSupabaseRealtime() every 5 s. Each call invokes WebSocketsClient::beginSSL() → begin(), which nulls _client.tcp/_client.ssl without deleting the live WiFiClientSecure (SSL context + open TCP socket) that the library's own retry had just allocated. This orphaned object leaks ~10-15 KB per cycle. After ~12 cycles the heap is exhausted; operator new inside the WiFiClientSecure constructor throws std::bad_alloc → std::terminate() → abort() → reboot. The reboot clears the leaked memory, and the cycle repeats indefinitely.
PZEM-C Hypothesis (CONFIRMED LIVE)
17 consecutive read cycles across 2 boots + 1 control capture: PZEM-A and PZEM-B report real voltage/current/frequency; PZEM-C is uniquely and consistently offline (0.0 V, 0.0 Hz, sensorOffline). Supabase cross-check confirms the same pattern. A diagnostic pin-swap has been prepared on a separate branch for testing.

5.2 The Leak Mechanism

Leak Source: WebSocketsClient::begin()
WebSocketsClient.cpp lines 59-64: 
void WebSocketsClient::beginSSL(const char * host, ...) {
    ...
    // WebSocketsClient.cpp:59-64
    _client.tcp = NULL;    // ← NULLs WITHOUT deleting
    _client.ssl  = NULL;   // ← NULLs WITHOUT deleting
    ...
}
Contrast with the library's own retry path (lines 252-262), which does delete properly: 
// WebSocketsClient.cpp:256
if(_client.tcp) { _client.tcp->stop(); delete _client.tcp; _client.tcp = NULL; }
if(_client.ssl)  { _client.ssl->stop();  delete _client.ssl;  _client.ssl  = NULL; }

Our loop() called initSupabaseRealtime() every 5 s:

  1. Library retry allocates a new WiFiClientSecure (SSL context + open TCP PCB) → connects to Supabase.
  2. Our loop() re-calls initSupabaseRealtime() → beginSSL() → begin().
  3. begin() nulls _client.tcp/_client.ssl without delete → orphaned object (SSL context + open socket).
  4. Library retries (no leaked pointer, clean alloc) → repeat from step 1.

6. The UART Flood

Symptom, Not Cause
The repeated seMode":3} / +08:00"} UART output is a symptom of heap exhaustion, not a separate bug. It appears in the 40-70 s exhaustion window and vanishes on clean boot. The flood is a TX-side corruption artifact: stale payload tail bytes are replayed at full UART line rate (~115200 baud) once the heap is corrupted and the serial TX buffer enters a bad state. The no-pulse control confirmed this is live serial output (5.5 MB / 60 s), not a port-closed artifact.
