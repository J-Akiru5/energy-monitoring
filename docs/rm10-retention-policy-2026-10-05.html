RM-10 — Retention Policy (Retain Indefinitely, For Now)

OD-2 resolved: telemetry is retained indefinitely; customer deletion revokes access, not history (ADR-08). The audit found the rule is already structurally enforced — no code, script, or migration deletes telemetry; every foreign key on or into a telemetry table is ON DELETE NO ACTION; and no RLS policy grants DELETE. No schema change was needed. What shipped is the missing piece: the policy in writing, a regression guard that fails if anyone adds a telemetry deletion path, and the re-verification SQL for the FK invariant.

The policy

POLICY

Retain indefinitely — for now

Telemetry (readings, alerts, blackout events, relay logs, alert state) is never deleted as a consequence of customer lifecycle. Deleting a customer revokes their access and closes the tenancy relationship; history stays. This is ADR-08's model with OD-2's concrete answer on numbers: no duration — retain indefinitely, revisit before the first commercial customer.

Two consequences worth stating plainly: (1) no retention job exists or is needed, so RM-10 has no cron, no pruning, and no duration arithmetic; (2) the only thing that could violate the policy is future code — a customer-deletion feature, a maintenance script, or a migration that deletes rows. The guard below exists for exactly that.

The guard

scripts/test-retention-policy.ts — read-only, no dependencies. It statically scans apps/, packages/, scripts/ and supabase/migrations/ for telemetry deletion patterns (PostgREST .from("<telemetry>")….delete() chains in code; DELETE FROM / TRUNCATE in SQL), and prints the FK re-verification query for the manual half of the invariant.

PASS — no telemetry deletion paths in code or migrations.

Manual FK re-verification (run in the Supabase SQL editor):
  SELECT tc.table_name, kcu.column_name, ccu.table_name AS parent, rc.delete_rule
  FROM information_schema.table_constraints tc
  ... WHERE tc.constraint_type = 'FOREIGN KEY'
    AND tc.table_name IN ('power_readings','alerts','blackout_events','relay_logs','device_alert_state');
  -- every delete_rule must be NO ACTION or RESTRICT
NEGATIVE-TESTED

The guard fails when it should

A temporary file containing supabase.from("power_readings").delete() made the scan report FAIL … .delete() on power_readings at offset 41; removing the file returned it to PASS. A guard that has never failed is not a guard.

Revisit trigger

  • Before the first commercial customer (OD-2): set concrete retention numbers (duration + data categories) and, if they differ from indefinite, build the enforcement. Until then this report is the policy.
  • Before any customer-deletion feature ships: deletion must revoke access, not cascade — the guard will catch direct deletes; the FK audit must stay clean.
  • RM-11 / RM-12 remain parked with their own triggers from the decision record.

Pipeline: RM-08, RM-09 and RM-10 are on develop only — staging/main deliberately not advanced, per Jeff. RM-01 (WVSU physical results) and RM-04's manual a11y walk remain with their owners.
