Findings

Fixed here

A · Session middleware blocked the firmware's pzem-config device call

packages/auth/src/middleware.ts's device-API allowlist (DEVICE_API_PREFIXES) listed /api/ingest, /api/heartbeat, /api/thresholds/esp32, and /api/relay — but not /api/devices. So the ESP32's authenticated GET /api/devices/:id/pzem-config was redirected to /login (307) before the route could validate its device token. This is pre-existing on main, not introduced by the promotion candidate. Fix in this branch: add /api/devices to the allowlist (session routes under it enforce their own auth and return 401 JSON), with two new middleware tests. Re-validation of this path requires the fix deployed to staging.

Behavior note

B · Unauthenticated API calls get 307 redirects, not 401 JSON

The staging-validation procedure expects 401 {"error":"Not authenticated"} for unauthenticated API calls (A8, admin routes). The session middleware intercepts them first and redirects to /login — so API clients receive an HTML redirect instead of JSON. Access is still denied, and this matches current main behavior. A cleaner design would return 401 JSON for /api/* paths in the middleware; that's a deliberate change worth its own decision, not a promotion blocker.

Minor

C · Malformed JSON → 500 (should be 400/422)

Discovered while diagnosing the harness bug: POST /api/ingest with an unparseable body throws in req.json() and returns a generic 500. A 400-family response would be more correct for clients. Cosmetic for devices (firmware always sends valid JSON); noted for a future pass.

Minor

D · Cross-tenant readings returns 200 with an empty list

The procedure's T5 expected 403 for cross-tenant access; /api/readings instead returns 200 {"readings":[]}. No data leak — the query is customer-scoped — but the API doesn't distinguish "no data" from "not yours". Optional hardening, not a blocker.
