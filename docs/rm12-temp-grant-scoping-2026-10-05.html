The capability audit — why this mattered

Before building, the actual capability set was enumerated rather than assumed: a temporary grant receives all 9 permissions cross-customer via the resolveAccess super-admin bypass. Reachable mutations included deactivate/replace controllers (token issuance), decommission/redeploy/cross-customer reassign (the new RM-09 flow), relay commands + config, thresholds, and billing. Reads and mutations shared permission gates (e.g. the admin device list requires manage_devices), so a naive "strip permissions" read-only mode would have blinded reads too — action-level checks were the right shape.

Mechanism

  • resolveAccess() now returns isTemporarySuperAdmin: true when the super-admin bypass came from an expires_at grant (decision #9) — permanent super admins and ordinary members are unaffected.
  • Mutating handlers reject the flag with 403 {"error":"Temporary Super Admin grants are read-only"} before any work happens.
  • GET/read handlers are untouched — the student demo keeps full cross-customer visibility, which is all the demo actually shows today.
  • The existing audit log (super_admin_access_log) records every temporary-grant resolution, including the blocked-attempt window.
