Controller Replacement: Transactional Revoke-then-Issue

RM-02. The revoke-then-issue flow that didn't exist now does — as a single Postgres transaction behind a service-role-only RPC. Replacing a controller retires every ACTIVE controller on the EMU (REPLACED + retired_at), rotates the legacy device token, and issues a new ACTIVE controller bridged to the same device. Verified on live with 16/16 checks, including an induced mid-transaction failure that proved the rollback: the EMU can never end up with two ACTIVE controllers or zero.

The rollback is the headline

An induced UNIQUE collision on the new token hash failed the RPC mid-function — after the retire and token-rotation steps had executed. Postgres rolled everything back: the old controller stayed ACTIVE, the device token was unchanged, and no orphan controller existed. That is the DoD's "never two ACTIVE, never zero" invariant, demonstrated rather than asserted.

The gap

Before this work, controllers.status supported 'ACTIVE' | 'REVOKED' | 'REPLACED' but no application code ever set a controller to either non-active state. A failed ESP32 could be physically swapped, but the old controller's token stayed valid and there was no way to issue its replacement — the exact gap RM-02 was filed against. RM-05 (device auth now accepts only ACTIVE controllers) made the missing flow more urgent: it provides the enforcement, this provides the operation.

Design

Two deliberate choices, both grounded in the existing schema:

  • Same legacy device row, token rotated. The EMU is the permanent identity; the device row is the legacy token holder that controllers bridge to. Reusing it preserves telemetry history, relay state/config, and blackout state — all keyed by device_id. The new controller bridges to the same device; only the credential changes.
  • Old controller → REPLACED, not REVOKED. The schema distinguishes them for a reason: REPLACED means "superseded by a new controller" (this flow); REVOKED stays reserved for disabling a controller with no replacement. Both are fail-closed under the auth path, so the security outcome is identical — the distinction preserves operational meaning.

The raw token is generated server-side in the wrapper (em_…, 128 bits of UUID randomness), returned exactly once — the same show-once contract as device registration. Only its SHA-256 is stored, computed inside the database function so the hash algorithm has a single source of truth.

The transaction

Everything below runs inside one Postgres function call — one transaction. Locks are taken in a fixed order to serialize concurrent replacements.

API surface & migrations

Database

replace_controller(p_device_id, p_new_token)

Migration 20261004000000_controller_replacement.sql. Service-role-only (revoked from PUBLIC/anon/authenticated). Uses built-in sha256() — no extension dependency.

Package

replaceController(deviceId)

Generates the show-once token, calls the RPC, returns { controllerId, deviceId, deviceToken }. Unit tests 4/4.

Admin API

PATCH /api/devices → replace_controller

Gated on the previously-unused replace_device permission plus the same ownership check as deactivate. Returns the token once; 409 when there is no active controller.
