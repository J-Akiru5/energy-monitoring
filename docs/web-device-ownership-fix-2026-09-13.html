Web Device-Ownership (IDOR) Fix — Release Note

Branch: fix/web-relay-device-ownership · PR into develop · 2026-09-13

Vulnerability

Insecure Direct Object Reference (IDOR) — cross-tenant device access. Four session-authenticated call sites resolved the caller's customer via resolveAccess() and then discarded it, acting on a deviceId taken directly from the query string, request body, or URL path param with no ownership comparison.
Call siteImpact before fix
GET /api/relay?deviceId=…Any member of any tenant with view_energy could read any tenant's relay state.
POST /api/relay (session path)Any member with control_relay could trip or reset any tenant's relay by substituting deviceId in the body.
GET /api/devices/[deviceId]/pzem-config (session path)Any member with view_energy could read any tenant's PZEM source config.
PUT /api/devices/[deviceId]/pzem-config (session path)Any member with view_energy could modify any tenant's PZEM source config.

The machine-to-machine X-Device-Token path and the X-Relay-Secret path were unaffected (scoped by token/secret, not session).

Fix

New reusable guard assertDeviceOwnership(access, deviceId) in packages/auth/src/deviceOwnership.ts, exported from the @energy/auth package:

if (access.isSuperAdmin) return;                 // cross-customer by design
const stamp = await lookupControllerByDevice(deviceId);
if (!stamp || stamp.customerId !== access.customerId)
  throw new DeviceAccessDeniedError();           // → HTTP 403

Applied at all four call sites. The relay POST path now parses the command once, verifies ownership, and only then executes the relay action — a cross-tenant request returns 403 before getRelayConfig, updateRelayState, or logRelayAction ever run. resolveAccess() itself was not modified.

Known follow-up (not fixed here)

apps/web/src/app/api/relay/config/route.ts (session GET/PUT) has the same permission-gate-without-ownership pattern and was outside this fix's file scope — schedule the same assertDeviceOwnership() treatment before the production release.
