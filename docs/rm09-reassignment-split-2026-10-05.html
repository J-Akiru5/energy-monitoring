RM-09 — Operational vs Commercial Reassignment

Applied and verified 12/12. The reassignment authority split from decision #2 now exists in code: operational reassignment (within the EMU's current tenancy) runs through redeploy_emu() and is gated by the dedicated reassign_emu permission; cross-customer reassignment is a new Super-Admin-only path, reassign_emu_cross_customer(), which moves the tenancy transactionally and carries ownership_party unchanged. The live test caught a regression in the very first apply — documented below, because that's the process working.

The split, as decided

PathScopeAuthorityMechanism
OperationalWithin the EMU's current customerCustomer Admin with reassign_emuredeploy_emu()
CommercialAcross customersSuper Admin onlyreassign_emu_cross_customer()
  • Gate change (Jeff, 2026-10-05): operational reassignment now requires the dedicated reassign_emu permission — previously manage_devices. Operators can manage devices but no longer move EMUs; Owners can. The admin route resolves the permission per action.
  • Ownership doesn't change the classification (Jeff, 2026-10-05): a PROVIDER-owned unit moved within its customer's tenancy is still operational. The split is by scope, not by ownership_party.
  • Precondition unchanged: both paths require the EMU to be DECOMMISSIONED first — reassignment is the redeploy counterpart, not a live edit.

The regression the live test caught

caught on first apply

My redeploy_emu re-declaration copied the pre-fix body

Migrations 20261004000003/...0004 exist because the original redeploy_emu had OUT-parameter ambiguity bugs: its RETURNS TABLE (…, emu_id, customer_id) makes those names variables, so bare customer_id/emu_id column references raise column reference "…" is ambiguous at runtime. I copied the original body into the RM-09 migration — reintroducing both bugs in the re-declared function, and inheriting them in the new one.

The live test failed on the third check immediately after the first apply. Corrected the migration (every colliding reference qualified — s.customer_id, b.site_id, i.emu_id, cu.id), re-applied with confirmation, and re-ran both suites: RM-09 12/12, RM-07 15/15.

This is the roadmap's own discipline doing its job: a live test run against the real database caught what a code read and a clean typecheck could not. The lesson is recorded here, not smoothed over — when re-declaring a function, re-read its full migration history first, not just its original definition.
