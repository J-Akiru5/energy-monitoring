Threshold breach now cuts power — and the dashboard says so

The relay auto-trip path is complete for overvoltage, undervoltage, and overcurrent, both cloud-side (within ~2 s) and on the ESP32 itself (no network needed). A tripped device now shows a distinct “Power cut — relay tripped” state in the admin and user dashboards and is counted offline — because the PZEM taps sit upstream of the relay, telemetry keeps flowing after a cut and freshness alone can never reveal it.

TL;DR

  • Reflash: the unit’s last verified flash (2026-09-12) predates the HTTPS relay-polling transport (2026-09-13). On that build the backend writes is_tripped but the relay never actuates. Current firmware source already polls; the new v4.1.0 bundle adds the safety fixes below.
  • Server: auto-trip now respects the relay master switch, re-trips on the next reading after a manual reset while the fault persists, classifies local trips correctly, and is covered by tests (previously zero).
  • Dashboards: admin Sensors/Overview and the web app (topbar + banner on every page) show the power-cut state with a human-readable reason.
  • Still manual: relay reset. Auto-reset and blackout-trip remain unimplemented and their UI controls are now disabled and labeled as such.

Why a reflash is required

  • Cloud auto-trip writes relay_state.is_tripped = true; the device learns about it by polling GET /api/relay every 2 s. That polling transport landed 2026-09-13 (d632619, 51fc323, fabbe3d), one day after the last verified flash — which relied on the removed, unreliable Realtime path.
  • There is no OTA: flashing requires PlatformIO and a USB laptop at the site.
  • The firmware previously read thresholds and trip flags only at boot; v4.1.0 refreshes them every 15 minutes, so config changes no longer require a power-cycle.
  • Cannot be fixed by configuration alone: local OC trip, per-condition flags, and the trip-acknowledgment logic only exist in v4.1.0.

Order matters — fix the live config before enabling trips

The live alert_thresholds table has historically contained duplicate rows (one with OV=200, below a normal 220 V supply) and reads previously had no ORDER BY, so the effective threshold could flip. Code now selects the lowest id deterministically, but the duplicate rows must still be collapsed before auto-trip is enabled, or the site could trip on normal voltage.

Risks & notes

  • Voltage stays live after a trip — the PZEM taps are upstream of the relay, so the cut is a software state, not a measurement. This is why the UI says “Power cut” rather than plain “Offline”, and why the banner notes the load is disconnected.
  • Re-trip semantics: the relay re-trips within one 5 s telemetry cycle if it is reset while the fault persists. This is deliberate — the load must not stay powered under an active fault.
  • Out of scope, observed: web GET /api/relay/config still lacks the ownership/scope check its comment claims; HIGH_POWER, blackout-trip, and auto-reset remain alert-only/disabled per the agreed scope.
  • No OTA: every future firmware change needs another USB flash; the version-in-payload addition exists to make that verifiable remotely.
