2. Health State Machine

Each phase (A, B, C) independently tracks consecutive NaN reads and good reads:

TransitionConditionTime @ 5s tick
HEALTHY → OFFLINEN ≥ 12 consecutive failures60 seconds
OFFLINE → HEALTHYN ≥ 6 consecutive good reads30 seconds

Counters reset on state transition. Mirrors the backend's 60s/30s dual-track incident engine windows.

3. Source Selection (1-Phase Mode)

AUTO Mode

  • Priority: A → B → C
  • Starts at source A
  • Sticky failover: once switched to a lower-priority source, stays there until IT fails
  • Re-evaluates priority from scratch (A→B→C) only when the active source goes OFFLINE

MANUAL Mode

  • Uses whatever source is configured in sourceState.manualSource
  • No silent fallback — if the configured source goes OFFLINE, reports NO_VALID_SOURCE

Problem

Addendum: UB Fix — String-Literal Mutation in 1-Phase Safety Trip

Bug

The 1-phase safety-trip path set localTripReason = "LOCAL_OVERVOLTAGE_PHASE_X" (string literal in .rodata), then used const_cast<char*>(strchr(..., 'X')) to mutate the 'X' in-place to the active phase letter. On ESP32, .rodata is flash-mapped and read-only. Writing to it is undefined behavior — a LoadStoreError at the exact moment a real voltage fault has been detected.

Fix

Replaced with a stack-allocated buffer and snprintf:

char localTripReasonBuf[40];
snprintf(localTripReasonBuf, sizeof(localTripReasonBuf),
         "LOCAL_OVERVOLTAGE_PHASE_%c", phaseLetter[0]);
localTripReason = localTripReasonBuf;

Addendum: HTTP Redirect Following on All Outbound Calls (Part A)

Bug

All four call sites in network.cpp used HTTPClient without calling setFollowRedirects(). Arduino's HTTPClient defaults to not following redirects. Vercel commonly answers with 307 for trailing-slash/protocol redirects — so all 3 retries in sendToCloud() would fail identically and the payload would be dropped silently. The same applied to the thresholds fetch, relay-state fetch, and reachability probe.

Fix

One line added to each of the four HTTPClient instances in network.cpp, immediately after http.begin():

http.setFollowRedirects(HTTPC_STRICT_FOLLOW_REDIRECTS);

HTTPC_STRICT_FOLLOW_REDIRECTS is deliberately chosen over FORCE: strict mode follows redirects while preserving the HTTP method for 307/308 (the Vercel case), so the telemetry POST stays a POST through a redirect rather than being rewritten to GET.

Addendum: Authenticated Relay-State Fetch on Boot (Part B — X-Device-Token)

Bug

fetchRelayStateFromCloud() sent zero auth on its GET to /api/relay?deviceId=..., while the route required a cookie session with no fallback for GET — a guaranteed 401 on every boot. The firmware silently fell back to NVS state: functionally safe, but the cloud's authoritative relay state was never actually used at boot.

Mechanism chosen: X-Device-Token

The boot fetch now sends the same X-Device-Token header/value the ESP32 already uses for telemetry. The GET handler validates it with the existing validateDeviceToken() (devices.api_key_hash = token AND is_active = true, the same gate /api/ingest uses) and returns the token's own device state. No new secret, no new NVS field, no new backend env var.

Why device-token over a shared secret:

  • Smaller blast radius — a leaked device token exposes exactly one device's relay state; a shared X-Relay-Secret would expose every device to anyone who extracted it from any firmware image.
  • Identity is intrinsic — the route resolves WHICH device from the token row, so no client-supplied identifier is trusted.
  • Zero new surface — reuses the credential the device already carries and the validator already in production.

Anti-spoofing scope

In the device-token path the deviceId query param is ignored entirely; identity comes from validateDeviceToken()'s row (device.id). A mismatched param is logged for audit ([/api/relay] Device token for <A> requested deviceId=<B> — ignoring query param), never trusted. The session/dashboard path is unchanged: session + resolveAccess("view_energy"), deviceId still required from the query.
