EMU Decommission / Redeploy

RM-07. The decommission → redeploy path now exists as two transactional database functions behind admin actions. Decommission ends the EMU's open installation and sets it DECOMMISSIONED; redeploy creates a new installation and reactivates it — both in single transactions, with cross-customer redeployment deliberately rejected as RM-09 territory. The migration is not yet applied to live (build-only phase, per the current hold); the live verification script is committed and ready to run.

Reality check

The roadmap's lifecycle string is longer than the schema

emus.status is defined as 'ACTIVE' | 'DECOMMISSIONED' (migration comment, line 67). The INVENTORY → PROVISIONED → ASSIGNED → INSTALLED chain has no schema representation and no code ever set it. This implementation makes the two real states operational rather than inventing state columns the schema doesn't have; the intermediate chain remains conceptual until a product decision says otherwise.

Design

  • Transactional: each operation ends/creates the installation and flips the status in one database function — a mid-failure cannot leave a decommissioned EMU with an open installation, or an ACTIVE EMU with none.
  • Same-customer only: the redeploy target's site must belong to the EMU's owning customer, and the building must belong to that site. Cross-customer redeployment is a reassignment — RM-09, blocked on OD-1 — so it is rejected rather than guessed at.
  • Controllers untouched: the device token stays valid across decommission/redeploy; telemetry can resume when the unit is physically reinstalled.
